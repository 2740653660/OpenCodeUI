# 简化上下文详情并将消息列表改为独立弹窗

- 创建日期：2026-08-02
- 优先级：中

## 背景 / 痛点

- 从上下文用量入口点击“查看详情”后，当前页面同时展示上下文统计、Token 明细、最近一次模型消息信息以及全部消息的原始 JSON，信息虽然完整，但整体较复杂，不方便用户快速看懂。
- 当前 Token 详情把输入、输出、Reasoning、缓存读写等多个项目同时展示，普通用户不容易判断整个会话实际消耗了多少输入和输出 Token，也不容易理解缓存效果。
- 当前页面直接展示消息列表，消息列表及其原始 JSON 对大多数用户并不常用，却会占据大量页面空间，干扰上下文统计信息的阅读。
- 仍然需要保留完整消息数据，方便用户在上下文异常、工具调用异常或 Token 统计异常时进行查看和排查。

## 期望效果

### 1. 简化 Token 详情

上下文详情页面展示整个会话累计的 Token 数据，默认只展示三个核心指标：

- 输入 Token
- 输出 Token
- 缓存命中率

统计口径如下：

- 输入 Token = 当前输入 Token + 缓存输入 Token
- 输出 Token = 当前输出 Token + 缓存输出 Token
- 部分模型支持缓存输出，支持时应计入输出 Token；不支持缓存输出的模型通常返回 0
- 缓存命中率根据整个会话的缓存输入数据计算
- 缓存写入数据不作为缓存命中率，但底层数据仍然保留，后续可在更详细的信息中查看

Token 数据统计范围为整个会话累计数据，不是只统计最近一次模型请求。

上下文使用量、上下文上限、使用百分比、是否为估算值、当前模型、消息数量和累计费用等信息继续保留，但需要重新组织层级，让用户能先看到最重要的上下文状态。

### 2. 将消息列表放入独立弹窗

- 上下文详情主页面不直接展示完整消息列表。
- 主页面只保留一个“消息详情”或类似的入口。
- 入口需要显示当前会话的消息数量，让用户知道里面有多少条消息。
- 点击入口后，打开独立弹窗查看消息列表。
- 消息弹窗中继续保留消息时间、角色、消息摘要、助手消息的 Token 和费用等信息。
- 单条消息可以继续展开查看详细内容。
- 完整的消息信息和原始 JSON 继续保留，但不作为默认内容直接铺开。

### 3. 页面排版方向

- 不采用所有信息从上到下连续堆叠的普通列表布局。
- 后续实现时需要重新设计信息层级和排版，让页面更有设计感、更直观。
- Token 三项数据应作为一个整体区域展示。
- 上下文使用量应当成为页面中最容易识别的核心信息。
- 消息详情作为独立入口和独立弹窗处理，避免影响主页面阅读。
- 具体采用卡片、分栏、图形化比例展示或其他布局方式，留到实际执行时再设计。

## 验收标准

1. 从上下文入口点击“查看详情”后，主页面不再直接显示完整消息列表。
2. 主页面可以看到整个会话累计的输入 Token、输出 Token 和缓存命中率。
3. 输入 Token 的统计包含当前输入 Token 和缓存输入 Token。
4. 输出 Token 的统计包含当前输出 Token 和缓存输出 Token；不支持缓存输出的模型按 0 计入。
5. 缓存命中率按照整个会话的缓存输入数据计算。
6. 上下文使用量、上下文上限、使用百分比、估算状态、模型、消息数量和累计费用等原有重要信息没有丢失。
7. 主页面存在消息详情入口，并显示消息数量。
8. 点击消息详情入口后，可以打开独立弹窗查看消息列表。
9. 消息弹窗中可以查看消息的角色、时间、摘要、Token、费用等信息。
10. 单条消息仍然可以展开查看详细内容和完整原始 JSON。
11. 主页面不再把所有统计项和消息数据连续堆叠展示，整体信息层级更清晰。
