# idea/ 文件夹规则（需求想法管理区）

这个文件夹是使用者（编程小白）的个人需求管理区：

- 使用者的想法以 Markdown 文件形式存放，每个文件一个需求。
- 需求状态用文件夹表示：待解决 → 解决中 → 已解决（或 已放弃）。
- 本文件夹随 fork 的 git 管理，但**绝不允许进入发往上游的 PR**。

## 目录结构

| 文件夹 | 用途 |
| ------ | ---- |
| `待解决/` | 新想到、还没开始做的需求 |
| `解决中/` | 正在解决的需求 |
| `已解决/` | 已完成的需求（含解决记录） |
| `已放弃/` | 决定不做 / 做不到的需求 |

## 记录新需求（铁律：没问清楚，不许写文件）

1. AI 在写入需求文件**之前**，必须逐项确认清楚：
   - **背景/痛点**：具体在什么场景、怎么操作时觉得不爽？要有具体例子，不能只说"感觉不好用"。
   - **期望效果**：希望变成什么样？有没有参照（某个软件、某个功能）？
   - **验收标准**：做完之后，用什么操作能验证"做好了"？
   - **范围**：涉及项目哪个区域（聊天界面 / 终端 / 文件浏览 / 主题样式 / 设置 / 其他）？
   - **优先级**：高 / 中 / 低？
2. AI 先用大白话把理解完整复述一遍，**得到使用者明确认可之后，才允许写入文件**。
3. 任何一项不清楚就继续追问（可以用举例、对比的方式引导），不允许带着疑问写入。
4. 使用者已提供完整清晰描述时可以减少追问，但"复述确认"这一步不可省略。
5. 需求文件写入后，**立即用 git 提交并推送**（使用者已确认此默认行为）：
   - 提交信息用中文，标题 + 正文（说明本次记录了哪些需求）。
   - 只提交本次新增/修改的需求文件，不带入无关改动。
   - 推送到当前分支对应的 `origin`（如 `main`）。
   - 若使用者临时有不同要求，按使用者最新指令执行。

## 需求文件格式

- 文件名：`YYYY-MM-DD-标题.md`，例如 `2026-08-02-深色模式配色调整.md`。
- 内容：按 `需求模板.md` 填写（标题、创建日期、优先级、背景/痛点、期望效果、验收标准、解决记录）。

## 状态流转

- 新需求 → 放入 `待解决/`。
- 开始解决 → 用 `git mv` 移到 `解决中/`。
- 解决完成 → 补填解决记录 → 用 `git mv` 移到 `已解决/`。
- 决定不做 → 用 `git mv` 移到 `已放弃/`。
- 移动文件必须用 `git mv`（保留历史，之后随时可查）。

## 需求解决 SOP（AI 解决需求时按此执行）

1. 从 `待解决/` 读取需求文件，用大白话向使用者复述理解；确认该需求是否仍然有效（可能已过时或已被上游实现）。
2. 与使用者确认"现在开始解决"，然后把需求文件移到 `解决中/`。
3. **默认**从上游最新代码创建独立分支（**无需询问使用者**——开分支是零风险操作，不影响任何现有代码，不需要征求同意，但要用一句话告知）：

   ```
   git fetch upstream
   git checkout -b <分支名> upstream/main
   ```

   分支名建议：`idea/<简短英文标题>`（如 `idea/dark-mode-palette`）。
   这样 PR 分支上不会包含 `idea/` 文件夹和个人规则文件，PR 天然干净。

4. 实现：一边做一边用大白话向使用者解释，每步说明"在做什么、为什么"。
5. 验证：运行 `npm run validate`（类型检查 + ESLint + 单测 + 生产构建）；必要时补充针对性验证。
6. 提交：中文提交信息，包含标题和正文（改动说明、验证结果、残余风险）。
7. 推送到 fork 的对应分支，并发 Pull Request 给上游：

   ```
   git push -u origin <分支名>
   gh pr create --repo lehhair/OpenCodeUI --title "<中文标题>" --body "<改动说明>"
   ```

8. 发 PR 前检查：PR 内容只包含本次需求的代码改动（红线：不得包含 `idea/` 与任何个人规则文件）。
9. 需求完成后：
   - 把代码改动合并回本地 `main`（使用者长期使用的版本）；
   - 在需求文件中补填"解决记录"（解决日期、分支、PR 链接、说明）；
   - 用 `git mv` 把需求文件移到 `已解决/`。
10. 向使用者汇报：改了什么、怎么验证的、PR 链接、剩余风险（用大白话）。

## 与使用者对话时的通用要求

- 全程中文、大白话，不假设使用者懂技术。
- 每一步向使用者解释在做什么；危险操作先征求同意。
- 使用者随时可能追加想法或调整优先级，优先按使用者最新指令执行。
